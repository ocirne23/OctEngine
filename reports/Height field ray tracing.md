# March the mesh, not the cascades

The literature gives no cross-vendor way to make a triangle BLAS for terrain much smaller, and no API has a height-field primitive [Likely]. The proven alternative removes terrain triangles from the ray tracing world and marches a height field in the shader: Snowdrop ships this, and Metro Exodus ships a partial form [Certain]. For OctEngine, the proposed three-level hybrid is not the best shape, because the cascades do not match the mesh at the ranges that the rays use [Certain]. The code gives a far cascade of about 129 m per texel with the default ring, not 16 m, and the 8 m cascade reaches only about 1.7 km from its centre [Certain]. The better height field is already in memory: the node vertices cover every LOD at the exact drawn resolution, and they cost only a small bound pyramid in addition [Likely]. BLAS cost on terrain is an estimate only, 61 to 370 MiB if every node has a compacted BLAS [Guessing]. The code builds a BLAS for every node, including nodes that the 4096 m TLAS range never traces, so the first memory saving needs no new shader work [Likely]. The first step is to measure real BLAS sizes per LOD. Do not start a march until that number justifies it.

## Two facts in the brief do not match the code

I read the repository to check the brief, and changed no code. The conflicts below change the evaluation, so please confirm them.

**The far cascade is not 16 m per texel with the default ring.** "Data map far range" is 8192 m, but it is only a floor. `TerrainStreamer.cpp:1499-1500` sets `farRange = max(terrainMapFarRange, 2 * meshHalfExtent)`, so that the cascade covers the whole mesh [Certain]. With `ringRadius` 128 and `chunkSize` 256, the range is at least 66048 m, which is **129 m per texel** over 512 texels [Certain]. A comment in `terrain_height.inc.glsl` agrees and gives "8 m near / 132 m far" [Certain]. The far cascade is 16 m only when the ring is 15 chunks or smaller [Certain, arithmetic]. `Docs/Context/RendererVK/Terrain.md` also describes the far cascade as the generator's coarse stage, "uncarved and smoothed" [Certain].

**LOD0 vertex spacing is 2 m by the default settings, not 1 m.** `TerrainGenerator.cpp:18` calculates spacing as `nodeSize / res`, and the defaults are 256 m and 128 quads [Certain]. A comment at `Terrain.ixx:340` says 1 m, and I think that this comment is stale [Likely]. I did not read a saved `.cfg`, and a saved value can change the result [Guessing]. With 2 m, the 8 m cascade matches LOD2, not LOD3 [Certain, arithmetic]. The conclusion below is the same with 1 m spacing, because the far cascade is still far too coarse.

The other brief facts hold: 129^2 vertices, 32768 triangles and about 333 KB per node [Certain]. The vertex total implies about 104 to 208 nodes, and the streamer docs say about 100 to 200 [Certain]. This table comes from `ringLodAt` with the default settings, and the band limits are approximate because the leaf rule works per node [Likely].

| LOD | Vertex spacing | Node edge distance | Compared with the 8 m cascade |
|---|---|---|---|
| 0 | 2 m | 0 to 461 m | Mesh is 4x finer |
| 1 | 4 m | 461 to 1024 m | Mesh is 2x finer |
| 2 | 8 m | 1024 to 2150 m | Same spacing, but the cascade fades out from 1720 m |
| 3 | 16 m | 2150 to 4403 m | Outside the cascade; the far cascade is 8x coarser |
| 4 to 6 | 32 to 128 m | past 4403 m | Past the 4096 m TLAS range; the far cascade is 129 m |

The cascade centre also lags the camera. The baker re-bakes on drift past range/4, with one job in flight, and a cold full near bake is about 1000 tiles at 1.5 s each, so a quick coarse pass ships first (`TerrainStreamer.md`) [Certain]. So the near cascade can differ from the mesh for seconds after a jump, and its good radius around the camera can be well below 1720 m [Likely].

## A compacted terrain BLAS costs 1.9x to 5.6x its vertices

No vendor, paper or engine publishes a BLAS size for a regular grid or terrain [Certain that the searches found none]. The best current data is one scene, Bistro, with compaction, PREFER_FAST_TRACE and fp16 positions ([Zeux](https://zeux.io/2025/03/31/measuring-acceleration-structures/)) [Certain]. The table applies those values to the 32768-triangle node, so it is an estimate [Guessing]. The total assumes a compacted BLAS on every node, scaled from the 33 to 66 MiB of vertices.

| GPU class | Compacted B/tri (Bistro) | Per node | Ratio to node vertices | All nodes |
|---|---|---|---|---|
| RTX 50 | 18.8 | 616 KB | 1.9x | 61 to 122 MiB |
| RTX 20 to 40 | 25.7 to 26.5 | 842 to 868 KB | 2.5x to 2.6x | 84 to 172 MiB |
| Arc B580 | 45.0 | 1.47 MB | 4.4x | 146 to 292 MiB |
| RDNA4 | 47.9 | 1.57 MB | 4.7x | 156 to 311 MiB |
| RDNA2/3 | 57.0 | 1.87 MB | 5.6x | 185 to 370 MiB |

A grid should land near the good end, because every triangle pairs cleanly along the shared diagonal [Likely]. Against this, fp32 positions can cost more than Bistro's fp16, and the author warns that bytes per triangle is approximate ([Zeux](https://zeux.io/2025/03/31/measuring-acceleration-structures/)) [Certain]. Driver changes alone moved RDNA3 from 88.4 to 57.0 B/tri ([Zeux](https://zeux.io/2025/03/31/measuring-acceleration-structures/)) [Certain]. Compaction keeps about half on NVIDIA: 52% average reduction ([NVIDIA RTXMU](https://developer.nvidia.com/blog/reducing-acceleration-structure-memory-with-nvidia-rtxmu/)), and 70.7 to 29.2 B/tri in one third-party probe ([praxis PR 303](https://github.com/gariasf/praxis/pull/303)) [Likely]. The engine has compaction on by default (`Render.ixx:695`), so the setting is already used [Certain].

**Hardware features do not solve this for all vendors.** Displacement micromaps were the natural fit, but NVIDIA says that `VK_NV_displacement_micromap` "is no longer available" ([NVIDIA](https://github.com/NVIDIAGameWorks/Displacement-MicroMap-SDK)), and Khronos marks it as deprecated ([Vulkan docs](https://docs.vulkan.org/refpages/latest/refpages/source/VK_NV_displacement_micromap.html)) [Certain]. `VkGeometryTypeKHR` has no height-field value ([Vulkan docs](https://docs.vulkan.org/refpages/latest/refpages/source/VkGeometryTypeKHR.html)) [Certain], and no public proposal for one appeared [Likely]. Cluster structures are `VK_NV_*` only in Vulkan ([Vulkan docs](https://docs.vulkan.org/refpages/latest/refpages/source/VK_NV_cluster_acceleration_structure.html)) [Likely]. DXR has a cross-vendor preview since 28 October 2026, but its only static memory figure is 723 to 527 MiB (27% less) on an RX 9070, with static scratch up from 1.83 to 526 MiB ([Microsoft](https://devblogs.microsoft.com/directx/clas-ptlas-preview/)) [Certain]. Microsoft says that this sample is a test playground [Certain].

A shared grid does match the cluster template model. A 128-quad node needs 256 clusters of 8x8 quads, or about 144 clusters at the 11x11 limit [Certain, arithmetic]. But a template mainly saves build time, because each CLAS still holds its own positions [Likely], and no source gives bytes per triangle for a CLAS [Certain]. Clusters therefore do not help AMD and Intel on Vulkan, where the BLAS is largest [Likely].

**AABB geometry through ray query is the weak option.** No published benchmark compares inline AABB handling with triangles, and none exists for a height field that I found [Certain that none was found]. The nearest numbers point both ways. Analytic tubes in an intersection shader were about 2x slower than triangles on Turing ([Kern et al.](https://arxiv.org/pdf/1912.08485)) [Certain]. An AMD proxy for coarse prisms ran at 0.72x and 0.97x of its dense reference, although its authors say that it underestimates the compute cost ([DGF paper](https://gpuopen.com/download/DGF.pdf)) [Certain]. In that paper the driver built 128-byte uncompressed nodes for procedural primitives [Certain]. Intel advises against traversal inside the shader and prefers many tight AABBs, which gives memory back to the BVH ([Intel](https://www.intel.com/content/www/us/en/developer/articles/guide/real-time-ray-tracing-in-games.html)) [Certain]. With ray query, an AABB also adds a candidate branch to all 7 shader files and returns control to the shader for each box ([DXR spec](https://microsoft.github.io/DirectX-Specs/d3d/Raytracing.html)) [Likely]. A height field needs no BVH to find its own cells, so a direct march gets the same result without that branch [Likely].

## Shipped engines prove the march, but no engine documents the near and far split

**Snowdrop is the closest shipped design.** Its deck states "Terrain does not have triangle representation for RT", and it marches the height field during intersection ([Koshlo, GDC 2024](https://media.gdcvault.com/gdc2024/Slides/GDC+slide+presentations/Koshlo_Oleksandr_Snowdrop_Custom_BVH.pdf)) [Certain]. PC uses DXR 1.1 inline trace, the scene radius is 4 km, and this drives indirect diffuse, reflections, long shadows and audio [Certain]. An excerpt lists the stages as BVH trace, then terrain march, but I did not see the order confirmed ([Kuenlin](https://media.gdcvault.com/gdc2024/Slides/GDC+slide+presentations/Kuenlib_Quentin_Raytracing_In_Snowdrop.pdf)) [Likely]. The radius is about the same as the engine's 4096 m TLAS range, which makes this a useful reference [Certain].

**Metro Exodus shows the simple merge.** It marches the terrain height map in the raygen shader, and a hit limits the real ray's distance ([4A/NVIDIA, slides 32-33](https://developer.download.nvidia.com/video/gputechconf/gtc/2019/presentation/s9985-exploring-ray-traced-future-in-metro-exodus.pdf)) [Certain]. The slide calls this almost free, and warns about precision and tolerances [Certain]. The slides do not say whether terrain also stays in the TLAS [Certain]. **Far Cry 6 goes the other way:** clipmapped terrain stays in the TLAS past the object range, and hardware confidence fades to 0 at the BVH edge to prevent popping ([AMD/Ubisoft](https://gpuopen.com/gdc-presentations/2022/GDC_Performant_Reflective_Beauty_Hybrid_Ray_Traced_Reflections_In_Far_Cry_6.pdf)) [Certain]. **Unreal** rebuilds Landscape to follow its morphing LOD, and a forum post warns of dark splotches when the BLAS and the drawn surface diverge ([Epic guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/ray-tracing-performance-guide-in-unreal-engine), [forum](https://forums.unrealengine.com/t/landscape-in-hardware-ray-tracing/2745488)) [Likely].

The candidate has no direct precedent. I found no shipped source with a distance handover from near terrain triangles or vertices to a coarser height field [Certain that none was found]. Snowdrop avoids a handover, because one path serves all ranges [Likely]. It also states that its RT world does not match the raster, so it cannot produce precise shadows, and it uses that world only past CSM range ([Koshlo, slide 52](https://media.gdcvault.com/gdc2024/Slides/GDC+slide+presentations/Koshlo_Oleksandr_Snowdrop_Custom_BVH.pdf)) [Certain]. NVIDIA gives the same split: diffuse effects hide a mismatch, while hard shadows and mirrors show it ([NVIDIA guide](https://dlss.download.nvidia.com/uebinarypackages/Documentation/UE5+Raytracing+Guideline+v5.4.pdf)) [Certain].

## The papers favour bound hierarchies, and the engine's march is not one

The research splits into fixed-step search, per-texel safety shapes and bound hierarchies. Only hierarchies are exact without an offline bake, and they are also cheap to rebuild ([Dick et al.](https://www.cs.cit.tum.de/fileadmin/w00cfj/cg/Research/Publications/2009/GPU_Ray-Casting/EG09AreasTerrain.pdf), [Oh et al.](https://faculty.digipen.edu/~gherron/references/References/SurfaceDetail/Pyramidal-Displacement-Mapping.pdf)) [Likely]. Dick is the closest match for streamed terrain: one pyramid per tile, built when the tile uploads, with only 1/3 extra memory [Certain]. His rays need at most about 50 steps on a 512 tile, against up to 1024 without the pyramid, for a speed gain of about 5 [Certain]. He chose this over cone maps because cone maps need an offline pass and much disk [Certain]. The max walk also does not miss a ridge at its stored resolution, even at steep grazing angles ([Oh et al.](https://faculty.digipen.edu/~gherron/references/References/SurfaceDetail/Pyramidal-Displacement-Mapping.pdf)) [Certain].

**`terrainSunVisibility` is a different method, even though it is called a cone march.** It does not read precomputed cones, as in [Dummer](https://faculty.digipen.edu/~gherron/references/References/SurfaceDetail/ConeStepMapping.pdf). It takes 8 or 10 steps that double from a start distance, and it reads one height at each step for a soft horizon (`terrain_height.inc.glsl`) [Certain]. Its comment accepts that a late step can miss an occluder [Certain]. It starts at 20 to 25 m in the two calls that I read, because it must clear the texel size and the relief that the map does not hold [Certain]. It returns visibility, not a hit distance [Certain]. So it stays right for far soft sun, but it is not a base for the other shaders [Likely].

**Coarse data has a known failure.** A level built by averaging can remove a ridge, and is not a bound of its finer data [Likely]. Dick builds his LOD tiles this way, and he can do this only because primary-ray error stays under one pixel [Certain]. This does not transfer to secondary rays [Likely]. The same limit applies to piecewise-constant hits: they give stair steps, so a shadow or mirror ray needs a real surface at the last step [Likely]. Lumen tried heightfields and dropped them for unreliable coverage, but that was for general meshes, and I saw only a search excerpt ([Wright et al.](https://advances.realtimerendering.com/s2022/SIGGRAPH2022-Advances-Lumen-Wright%20et%20al.pdf)) [Likely].

**The honest counter-evidence is speed.** RMIP's Table 1 implies that its height-field method is 4x to 105x slower than uniform triangles (my division) [Likely], and the uniform tessellation rate is not in the main text [Certain]. Its authors say that for moderate maps and static content, pre-tessellation with hardware ray tracing "remains the method of choice" ([RMIP](https://perso.telecom-paristech.fr/boubek/papers/RMIP/RMIP.pdf)) [Certain]. A terrain node is moderate and static between streaming events, so this applies more than a reader may want [Likely]. Dick's ray caster also lost in speed and memory to the rasterizer on the smoother Utah data [Certain]. But RMIP's cost includes curved base meshes, and terrain is a planar height field, so the gap should be smaller [Likely]. No paper gives ms per Mray for a plain terrain walk at game scale [Certain that none was found].

## The candidate's weak part is its cascades, because the mesh already holds the data

Evaluated against this evidence, the three-level hybrid has one correct idea and two weak levels. The correct idea is that vertices are the near height field [Likely]. The weak levels are the cascades, for four reasons.

The first reason is range. The rays run about 4 km at most: the TLAS range is 4096 m, and the water reflection range is 3000 m (`Render.ixx:981`, `Ocean.ixx:98`) [Certain]. In that span the mesh is LOD0 to LOD3. The 8 m cascade is equal to the mesh only for about 1 to 1.7 km, and the 129 m cascade is 8x coarser than LOD3 where it takes over [Certain, arithmetic]. The second reason is that a cascade is not a bound. Each texel is a sample of the generator, with no min or max, so the ray can pass over a mesh ridge or stop on terrain that the mesh does not have [Likely]. The third reason is handover. No paper solves a ray that crosses nested camera-centred levels, and a ray can start under the coarser surface and hit at once [Likely]. The fourth reason is time: the baked map lags the mesh by a bake, and the mesh does not lag itself [Likely].

A new 16 m height-only cascade is cheap, at 1 MiB in R32F [Certain, arithmetic]. It would fix the range and leave the other three problems [Likely]. It would also copy data that LOD3 vertices already hold [Likely].

**Use the vertices as the height field at every range.** A `TerrainVertex` holds float world Y and a normal, in a regular row-major grid [Certain]. `grassGroundHeight` already reads the exact drawn triangle, with the same diagonal as `TerrainGenerator.cpp` [Certain]. Three shaders bind `in_terrainVertices` already and fetch it for a terrain hit: GI trace, `water_scene.inc` and the film [Certain]. `rt_shadow.inc.glsl`, `rtao.cs.glsl`, `vol_scatter.cs.glsl` and `rain_occlusion.cs.glsl` do not name it, so these need a binding or an includer that has it [Certain]. The range is limited today: the ground table is 16^2 base chunks, with the list filled only to the grass range plus 16 m (`Vegetation.md`) [Certain]. A table for 4096 m needs about 33^2 entries, or about 17 KB per frame slot at 16 B each [Guessing, entry size assumed]. It already handles a base chunk inside a bigger node as a sub-grid [Certain].

This design needs one new thing: bounds. Dick's pattern fits, with a pyramid per node when it is generated, stored as min and max rounded outward [Likely]. With 4x4-quad leaf bricks, a node has 1365 entries: 5.5 KB in RG16, or 10.9 KB in RG32F [Certain, arithmetic]. That is about 0.6 to 2.3 MiB for all nodes, against 61 to 370 MiB of estimated BLAS [Guessing]. The same data removes the handover, because a march and a BLAS read the same unstitched vertices, so both give one surface [Likely]. A height field also defines occupancy for each XZ position, so a ray below the surface at a node edge is a hit, and a T-junction crack cannot leak [Likely]. A ray that starts on a fine node beside a coarser neighbour can get a false hit at that edge, and it needs a bias that scales with LOD error [Likely]. No shipped source gives a number for this bias [Certain that none was found].

| Option | Extra memory estimate | Vendors | Shader work | Surface error | Main evidence |
|---|---|---|---|---|---|
| A. All nodes, full BLAS (today) | 61 to 370 MiB | All | None | None | Unreal, Far Cry 6 |
| B. BLAS only inside TLAS range | About half of A | All | None | None | Reference residency in Unreal |
| C. B, plus half-resolution BLAS on LOD2 and LOD3 | About a third of A | All | None | LOD error, needs a bias | Metro: 4x smaller BLAS meshes |
| D. BLAS on LOD0 and LOD1, vertex march past them | About 30% of A | All | 7 files | None | Combination of parts |
| E. No terrain BLAS, vertex march everywhere | 0.6 to 2.3 MiB | All | 7 files | None | Snowdrop, Dick |
| F. Candidate: vertices, then cascades | 2 MiB plus a new cascade | All | 7 files | Large past 1 km | No precedent |
| G. AABB BLAS with ray query | Not published | All | 7 files, candidate branch | Depends on the data | RMIP, no ray query data |
| H. Cluster templates | Not published | NVIDIA on Vulkan | Build path | None | DXR preview sample |

The node fractions in B, C and D are my estimates from the band table, and the count per LOD must be measured [Guessing]. The evidence that B is real: `createTerrainMesh` passes `raytraced = true` for every node, and `recordBuildBlas` builds every new mesh, while the TLAS only excludes instances by range (`RendererScene.cpp:424`, `RendererRecord.cpp:1045-1054`) [Certain for the code path]. I did not trace whether a later step frees those BLASes [Guessing]. For C, a second shared index range at stride 2 can build on the same vertex buffer, so it needs no new vertex data [Likely]. `Terrain.md` already records a bed mismatch in the river trace, and a coarser BLAS makes that class of error larger [Likely].

**Order the work by tolerance and by ray shape.** Rain occlusion rays read a distance through `rayQueryGetIntersectionTEXT`, and the rain direction suggests near-vertical rays, which are a march's best case ([Dummer](https://faculty.digipen.edu/~gherron/references/References/SurfaceDetail/ConeStepMapping.pdf)) [Guessing]. RT shadow, RTAO and volumetric scatter stop at first hit, and their rays need no attributes [Certain]. GI needs a normal, and a march can compute the vertex indices directly from the cell, so the existing fetch code stays [Likely]. Water reflection is the worst case: long grazing rays over flat ground leave the hierarchy little to skip ([SIGGRAPH 2023 paper](https://www.dgp.toronto.edu/~hsuehtil/pdf/diff_hpt.pdf)) [Likely], and mirrors tolerate no error [Certain]. Move it last. Past the TLAS range, keep `terrainSunVisibility` as it is [Likely].

For the merge, march first and pass the hit as `tMax` to the ray query, as Metro does [Certain for Metro]. Rays that miss still pay TLAS cost ([Far Cry 6, slide 70](https://gpuopen.com/gdc-presentations/2022/GDC_Performant_Reflective_Beauty_Hybrid_Ray_Traced_Reflections_In_Far_Cry_6.pdf)), and terrain is the first hit for many rays, so a tighter `tMax` should give back some march cost [Likely]. No source compares this order with the BVH-first order [Certain].

## Gaps and sources not read in full

**Not read in full:** the Kuenlin Snowdrop deck, the AC Shadows SIGGRAPH 2025 deck and the Lumen 2022 deck are over the fetch limit, so those facts are excerpts only. Tevs et al. 2008, Baboud et al. 2012, Timakov and Mikhaylyuk 2023 and Ogaki 2023 are abstract only. TFDM is its abstract plus the numbers that RMIP reports. Drobot's QDM chapter was not read. GPU Gems 3 chapter 18 and Hoetzlein 2025 came through a summarising tool, and the Hoetzlein timing columns were ambiguous, so this report does not use them. I read only the first 100,000 characters of the DXR specification. The Blackwell whitepaper does not mention a DMM engine, but its block diagram could not be viewed, so "Blackwell removed DMM hardware" is an inference [Likely].

**Evidence that does not exist or was not found:** a BLAS size for a grid or terrain on any GPU; bytes per AABB in a BLAS; ray query against intersection shader on one scene; CLAS bytes per triangle; a grazing-case step count at game scale; a toroidal min-max update with measured cost; traversal across nested clipmaps for secondary rays; and a numeric terrain bias. I found no public statement on terrain in REDengine, Northlight or Decima, and the search for these was limited. Terrain in AC Shadows remains unverified. Most B/tri data dates from 2021 to 2025, and no re-run on 2026 drivers was found.

**Engine work not done:** I read the code in spots only and did not run anything. All engine BLAS values here are estimates. I did not confirm how much the march costs per ray, whether the buffer reads are slow at 20-byte stride, or how nodes retire while a frame uses them. The current ground table lives for one frame, which is a useful pattern for that case [Certain].

## Recommendation and first measurement

**Reject the cascade levels of the candidate, and do not start with a march.** First apply option B, if the measurement confirms it, because it costs no shader work and no image quality [Likely]. If the remaining BLAS memory is still too high, try option C next, as it needs no new path through the 7 files [Likely]. Move to option E, the vertex march, only when BLAS memory stays a real problem. Prototype it in `rain_occlusion.cs.glsl`, then RT shadow, and compare with ray query. Option D is the fallback if the march is too slow at short range: the shared vertices make its handover free of surface error [Likely]. This order disagrees with a pure memory reading, because the papers warn that triangles are often much faster [Likely]. As a working limit, I suggest that the march starts only if in-range BLAS memory exceeds about 2x the terrain vertex memory on the lowest target GPU; this is my judgement and has no source [Guessing].

**The first measurement is BLAS size, not GPU time.** For the one shared 32768-triangle grid and for each resident node, log `accelerationStructureSize` and `buildScratchSize` from `vkGetAccelerationStructureBuildSizesKHR`, plus the compacted size from the query that `recordBuildBlas` already uses. Group them by LOD, and log for each LOD the node count and the number of nodes with an active TLAS instance. Run this on each vendor GPU that is available, and at least on one NVIDIA and one AMD GPU if possible. This replaces every estimate in the first table, gives the true value of option B, and costs one short run with no timing. The second measurement, only if the numbers justify it, is rain occlusion in ms per Mray for a march against ray query, with `Tools/profile.ps1` under the project's GPU rules.
