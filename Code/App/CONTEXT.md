# App
Documentation for `Code/App` — the testbed executable (main.cpp, `App.Lobby`, `InputControls`, `App.ProfileDump`). Read `.claude/CLAUDE.md` first (rules, building, style, dependency direction). The frame-loop ordering rules (kick/join windows, post-update jobs) are documented in the owning libraries' CONTEXT.md files (RendererVK, Spatial, Threading, UI, Entity).

## Main menu and lobby
* MAIN MENU: App.exe with NO mode flags boots into a fullscreen start screen (`UI:MainMenu` — co-op/PvP/sandbox buttons, a "Host a server" checkbox (shows the endpoint other clients dial: seeded with `netGetLocalAddress()` + the launch port, upgraded to the EXTERNAL IP when `netGetExternalAddress()` — run on a detached thread with a shared_ptr result block, polled in the loop's menu block — lands; the LAN address moves to a dim note line, failure keeps the LAN address) or an address field (`ip[:port]`, empty = offline), a Quit button, and a SETTINGS page built from the tweak registry: curated per-section category-prefix tables in MainMenu.cpp, dev branches (Debug/Stress/Stats/Cheats/Emitter/V3 + Time/Paused) filtered, rows drawn by the exported `drawTweakVar` shared with the TweakPanel, onChange deferred through the TweakPanel's list). While active the widget pass draws ONLY the menu (viewport rect = full window, no editor panels, no prepare jobs); the menu just records a `MainMenuAction` — main() polls `takeMainMenuAction()` after the post-update join and runs `startMode` (a lambda shared with the command-line path: network host/join, testbed or game world content, `oc::optional<GameMatch>` emplace) in the pre-kick window, under a one-shot `AllowMainThreadIO` (the F10 pattern). Any of --game/--server/--connect/--headless, --scenario or an unattended flag skips the menu and starts directly; a failed host/join leaves the menu up. During the menu phase the testbed keys are muted (`setGameMode(true)`) and free flight is paused; the mode start restores both per the selection. The old one-shot startMode is SPLIT: `startNetworkFor` (host/join + the server join hooks — game modes wire lobby+GameMatch together, lobby FIRST) and `startWorldAndGame` (content + `oc::optional<GameMatch>` emplace).
* LOBBY (`App.Lobby` — `LobbySystem`, a plain stack local in main; UI = the MainMenu's lobby page, `LobbyView`/`LobbyAction` snapshots polled like MainMenuAction): a MULTIPLAYER co-op/PvP pick from the menu enters the lobby instead of starting (offline picks and the sandbox start immediately; command-line runs never lobby — a CLI game server calls `lobby.markStarted` so menu clients joining it still get the go signal). Server-authoritative over reliable events: LbR (client ready toggle), LbG (start request — server re-validates all-ready), LbS (full state broadcast on every change: coop/countdown/started flags + the host's CO-OP MAP SETTINGS (seed/fill/lanes — the lobby page's "Map" block: host-editable widgets committing on release as a `SetMapSettings` LobbyAction, read-only line on clients; at launch main hands them to the host's GameMatch via `setMapSettings` before spawnWorld; clients still generate ONLY from the game's GMp event, so the lobby copy is display) + roster with ready bits; clients ignore relayed LbR/LbG via sender != 0), LbX (countdown done — launch). Ready check per player, anyone may Start when ALL are ready → 3 s countdown (`c_countdownSeconds`, real clock); ANY un-ready or a mid-countdown join cancels it. The HOST's mode is authoritative — a client's GameMatch coop flag comes from the first LbS, and that client CONSTRUCTS its GameMatch inside the dispatch (world visible behind the lobby; `updateWindowed` is gated on menu-inactive so game input/camera/HUD stay off) — at countdown end the server spawns its world and calls `game->onClientJoined` for every lobby client (capsules + world replay; a client joining a RUNNING game gets LbS(started) BEFORE the replay via the join-hook order). LEAVING: the lobby page's Leave button (also on the "Connecting..." page — the way out of a dead address) is a `LobbyAction::Leave` that main turns into `exitToMenu` (host: the server closes and every client sees a disconnect; client: just its disconnect, the server's onClientLeft hooks drop it from the roster / the match). A CLIENT whose server goes away (host left via Leave or the escape menu's Exit to menu, link death) gets `NetworkManager::setOnServerLost` (fired inside receive(), before the manager's auto-reconnect) — main only sets a flag there and runs `exitToMenu` at the next loop top (pre-kick window; the shutdown ends the reconnect) with a "Disconnected from the server" status line on the front page; command-line clients keep the auto-reconnect. KNOWN limit: a CLI `--game --connect` client in a menu-hosted lobby never readies (its lobby is inert — the host cannot start).

* CHAT (`App.Chat` — `ChatSystem`, a plain stack local in main next to the lobby; UI = `UI:ChatPanel`, a `ChatView` snapshot pushed by main ONLY when `chat.generation()` changed + `takeChatOutgoing()` polled every frame): a text chat drawn EMBEDDED in the lobby page and as a translucent OVERLAY in the game layout's bottom-right corner (co-op and PvP; single player fires locally only). ONE event, "ChM" [string ≤200 chars] reliable: a sent line is `fireNetworkEvent`'d (the local fire = our own log entry, the server relays to the other clients re-attributed to the real sender); main's dispatcher routes "ChM" to `chat.handleNetEvent()` BEFORE the Lb*/game split. Both server-side event filters admit it (`ChatSystem::allowsEvent` in the lobby filter; the Game layer's Gq* filter repeats the 256-byte cap by hand — Game cannot import App). Names are "Host"/"Player N" like the lobby roster. Keys: Enter with no active widget opens the input line (read through ImGui, so it works while the game viewport owns the keyboard), Enter sends, Esc cancels; in-game both refocus `##GameViewport` so the viewport-focus hotkey gate re-arms — while typing the grid hotkeys are off because the viewport is not focused. The log survives lobby → match and resets on exit-to-menu (`chat.reset()` + `ui.clearChat()`); 100 messages kept.

## Testbed keys (InputControls)
* F5 reload shaders, F6 recompile script, F7 write the profiler text report (see Profiling); T/R/G gizmo modes; Pause/Break toggles the global simulation pause (see Core's GLOBAL PAUSE — also in game mode)
* 1 clear test lights, 2-6 spawn one light of each type at the camera, 7 burst 100 points (all share one lazily built template; values live on the component, deliberately not serialized). While the game HUD's hotbar is ACTIVE (see Core.GameHud) keys 1..9,0 select hotbar slots instead and the testbed meanings above are skipped
* 8/9 spawn+throw a physicsCube/physicsSphere; 0 hangs an 8-cube joint chain from `staticBody()`
* N spawns a force emitter from the Force/Emitter tweak values; M re-applies those tweaks to the LAST spawned emitter; H 500-emitter stress burst; F physics sphere carrying a bubble; J territory query grid; B clear
* P toggles GI probe debug, O cycles its mode, L aims the sun down the camera forward
* C toggles player control: on a network client it drives the locally-owned capsule (see Multiplayer) with the same first/third-person camera follow; single player / server it spawns + possesses a local upright player capsule (playerCapsule.pre, `LockRotation`) — camera-relative WASD velocity steering, Space jump off a ground raycast, LShift sprint, V toggles first/third person (third pulls in on a wall raycast), camera follows the interpolated body pose ("Player" tweaks: eye height/third distance/sprint; move params shared with "Network/Player"). `InputControls::applyPlayerCamera` overrides the frame camera right after the fly camera in main
* Network: U (server) throws netPhysCube.pre, C (client) toggles player control, K fires "NetPing"
