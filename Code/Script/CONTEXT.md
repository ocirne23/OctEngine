# Script
Library documentation for `Code/Script`. Read `.claude/CLAUDE.md` first (rules, building, style, dependency direction). The DSL language reference + DslCompiler usage is `Code/DslCompiler/CONTEXT.md`.

* Visual scripts compile to real DLLs: `ScriptHost` (`Globals::scriptHost`, Core-only) compiles a .scr with the installed MSVC toolchain (vswhere → vcvars64.bat, `cl /LD /std:c++20 /MD /Od /Zi /DSCRIPT_BUILD`, `/FI ScriptAPI.h`) into `Assets/Local/Scripts/`, caches by path, hot-reloads (`getOrLoad(path, forceRecompile)`) — F6 or a Script Editor save; live entities hot-swap. On failure the previous build is kept. A .scr is BODY-ONLY C++ (no `#include`/`#define`)
* COOKED alternative (`SCRIPTS_STATIC`, off by default): `Code/AppScripts` generates one aggregate TU that `#include`s every `.dsl` (only — .scr is not cooked) into its own namespace and compiles it INTO the engine (`/WHOLEARCHIVE:AppScripts` keeps the registrations). `REGISTER_*()` markers at the end of each .scr feed a static-init registry `getOrLoad` resolves from instead of cl/LoadLibrary — whole-program-optimized. All-or-nothing: one broken .scr fails the aggregate
* A .scr IS the generated C++ (entry points `OnSpawn`/`Update`/`OnDestroy`/`OnEvent`/`OnPhysicsEvent` + `ScriptEventCount`/`ScriptEventName`/`ScriptDataSize`) with the node graph appended as `//@graph`/`//@node` comments — the NodeEditor regenerates code from the graph; the file is also hand-editable
* .scr / the NodeEditor path is REMOVED from the running editor: no node panel, no `UI::m_scene`, no .scr open/create routes (the `NodeEditor/` sources remain in the tree for reference and still compile as unused partitions). A .scr shows as a plain text file in Content, isn't offered by script pickers, and isn't cooked; `ScriptHost` itself would still compile one if a .pre carried the path, but nothing authors that anymore. When Claude is asked for a script, author a .dsl via DslCompiler — never a .scr
* `ScriptAPI.h` is the host↔DLL ABI: C linkage, PODs/glm/raw pointers only. The `ScriptContext` function table is APPEND-ONLY (cached DLLs must keep working). Scripts see a layout-compatible `Entity` MIRROR (pos/scale/rot/parent only; offsets static_asserted in ScriptContext.cpp). Components a script can't name go through opaque handles: `ctx->entityGetForceComponent(entity)` returns `void*`, `ctx->forceGet*/forceSet*(handle, ...)` cast back host-side (the NodeEditor hoists the handle so lookup runs once)
* `ScriptModule`: DLL entry pointers + event names + data layout (`dataLayoutId`, `dataFields`, `requiredComponents`); don't cache function pointers across reloads
* DSL surface: `math.*` namespace (all scalar math, ANGLES IN DEGREES; `ocInverseLerp/ocRemap/ocMoveTowards/...` in ScriptAPI.h avoid double-evaluation; randomness is one ENGINE-side generator so hot-reload doesn't reset it). `self.animator.setFloat/setBool/setTrigger/...` — animation is the animator's surface, nothing names a clip. A getter-call member MUST register `writable=false` (a writable member's emit is used verbatim as an assignment target)
* ScriptData: `//@@data [private|public] <type> <name>` fields (default Hidden); exposed fields surface through `ScriptDataFields()` (`OcScriptField[]` — the only engine-side layout description). Properties panel edits them LIVE (never serialized); Entity Editor authors INITIAL values (text under `Component Script`/`Data` in .pre, re-applied by `applyInitialValues` after every `syncScriptData` reallocation)
* DSL containers: `T[]` arrays live ENGINE-side (`OcArray` generation-tagged handles; storage survives hot-reload). No unchecked reads: `foreach [ref] T x in c` iterates, `ifexist [ref] T x in c [at k]` is the single checked lookup. POD arrays resolve once to a span (`ctx->arraySpan`) — one ABI call per loop, elements are plain loads, `ref` binds a real C++ reference into the span; Entity/String arrays keep checked per-element reads. THE SPAN IS ONLY VALID WHILE THE ARRAY DOESN'T GROW — `checkContainerMutations` (ScriptLoader) enforces it as a whole-document fixed-point over the call graph (a push through a parameter poisons the function for every caller, conservative on purpose) and runs from BOTH `save()` and `load()` (the editor's Compile & Run path never parses); push/clear on a container an enclosing loop reads is refused. `ref` is refused on handle types and non-writable containers; non-`ref` elements can't be assigned. The editor-side grey-out (`ScriptLang::isContainerIterated`) is still syntactic — transitive mutation through a user function is authorable and gets refused at load
* `//@@require` is enforced LIVE by `requirementsMet` (mask test) at every entry point — not latched at spawn (hot-reload mutates the module in place). `OnSpawn` runs once, the first frame the entity qualifies (`onSpawnRan`); `OnDestroy` pairs with that flag, never the live check. `syncScriptData` re-allocates + refills require slots + clears `onSpawnRan` when the module layout changed; `syncScriptDataLive` (every post-spawn entry point) also re-registers the event listener (its stored pointer would dangle)
* FAULT CONTAINMENT (`OC_SCRIPT_FAULT_CONTAINMENT` at the top of ScriptComponent.cpp, default 1; 0 = raw calls, faults crash normally for clean dumps): every entry-point call goes through SEH-guarded invokers (`invokeScript*` in ScriptComponent.cpp — plain `__try`/`__except`, no C++ exceptions, zero cost until a fault): a hardware fault in script code (int divide by zero, stale pointer) marks the module `faulted` and logs instead of crashing. `requirementsMet` folds the flag in, so the script stops running everywhere (OnDestroy included — its data may be half-written); ScriptEventManager's direct OnEvent path checks it itself. A successful (re)load clears it (`loadDll`), so F6 / Compile & Run is the recovery. Deliberately unguarded: breakpoints, stack overflow, C++ exceptions (filter whitelist in `scriptFaultFilter`). Float div-by-zero never faults (FP exceptions stay masked — inf/NaN propagate)
* There is NO null in the DSL: absent values are OPTIONAL types (`Entity?`, readable only via `ifexist`); dead entities in arrays report a lookup miss
* The DSL subsystem (data model, autocomplete, bindings registry, save/load, C++ transpiler) lives under `Private/DSL/` as partitions re-exported from `Public/ScriptHost.ixx` — editor-agnostic; UI's Script Editor panel (`import Script;`) is its consumer. Types an outside importer needs must be `export`ed (partitions leak unexported types across same-module files — easy to miss)
* `DslCompiler <input> [output.dsl] [--compile]` (`Code/DslCompiler`, console exe) — THE way Claude authors .dsl files: write only the DSL text, the tool validates (same loader as the editor, full binding vocabulary), transpiles, and writes the exact file the editor's Save produces. USAGE + FULL LANGUAGE REFERENCE: `Code/DslCompiler/CONTEXT.md`. Raw input = single-`@` directives (`@require`/`@data`/`@event`) + TAB-indented code; the tool prefixes every line with `//@` (which is what turns `@require` into the stored `//@@require`) and wraps in the markers. An existing .dsl as input = normalize + regenerate C++ in place. `--compile` cl-compiles + loads the output through the real ScriptHost pipeline (the F6 path) — the final check that the script loads in the engine as-is. Errors print `<input>(<line>): <what>`; relative paths resolve against Assets/; exits via `_Exit` (nothing initialized, global dtors assume engine teardown order)
